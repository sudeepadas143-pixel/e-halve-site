ORDERS

Every payment starts as an order, and every order starts as an account the program writes during a tick — never before, never after. An order names a handle by hash, an amount in cents, and the tick it came from. It opens the moment it's written. From there it can only move to one of two places: settled, once the hand pays it and proves it, or void, if the handle unfollows before that happens.

status

There's no expiry on an order. Most systems that write payment obligations onchain put a clock on them — claim within some window or forfeit. This one doesn't, because the obligation isn't the follower's to chase. An order stays open for as long as it takes the hand to get to it, and the roster proves at any later point whether the handle was still eligible when the order was written, so there's no ambiguity to resolve by expiring things early.

Void is the only way cents come back to the clock outside of a tick itself. If a handle unfollows while their order is still open, the order is marked void and its cents return to the clock's outbound balance, ready to be spent by the next tick instead of sitting stuck against an obligation nobody can collect. This only happens pre-payment — once an order is settled, it's a historical record, not a claim, and nothing about it changes afterward.

Settlement is one-directional and one-way-checked. The hand calls settle with a payment post id, the program marks the order settled, and the cents leave the outbound vault. The order itself doesn't verify that the payment actually reached the right handle for the right amount — that verification lives on the hand page instead, where every settle call is checked against the order it claims to be paying. Splitting the two apart is deliberate: an order is a fact about what's owed, settlement is a fact about what happened, and conflating them would make it harder to catch a hand that pays wrong.
